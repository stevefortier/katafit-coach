# Coach settings save, then stop / restart

Settings Save, persona-history Restore and legacy `POST /api/rollback` share one server-owned transition. The browser never races separate Stop, Save and Run calls. Saved-revision Preview is not a transition: see [non-disruptive preview](#non-disruptive-preview).

- No consent precondition: a running Coach or active native Pi never blocks a valid save (a legacy `confirmRestart` is accepted and ignored). Studio sends the mutation directly, with no status preflight or confirmation dialog. An explicitly chosen Restore still confirms only which drafts it replaces.
- The durable local write happens first and the HTTP answer returns right after it. Stop (native teardown, background Coach, Worker presence) and the restart then continue in the background as one serialized continuation reported through `GET /api/status`; the answer never waits for a stop, cleanup, presence report or reconciliation. A new Worker captures the resulting endpoint, model, vision flag and credential together.
- Running intent is captured after the write (an intentionally stopped Coach stays stopped) and inherited by a newer save that supersedes the continuation, including one applied during a held stop or start. Intent survives a pending or failed restart, so the next save retries it; only a successful start, Run or Stop settles it. The latest save owns the eventual run or an explicit `restartPending`/`COACH_RESTART_FAILED`.
- While a continuation runs, Run, Stop, preview, manual upgrade, confirmed maintenance quiesce and native-ticket admission get `OPERATION_IN_PROGRESS`; a valid settings save does not. Only one local settings write runs at a time (a save arriving during another's write gets `OPERATION_IN_PROGRESS`). Studio locks settings editors only while its own settings request is outstanding or an update replaces the process, never for a continuation or a preview. No user chat, action, or terminal input is replayed.
- Persona restore copies only persona fields into a new revision. Legacy rollback retains Store's configuration/credential binding rules; it is an API compatibility path, not an extra Studio editor.

## Non-disruptive preview

`POST /api/preview` never stops, starts or restarts the worker and never closes native sessions, on success, failure, Cancel, disconnect or timeout. It needs no confirmation (a legacy `confirmRestart` is accepted and ignored), records no `lifecycle`, and a lost reply leaves no lifecycle uncertainty in Studio. It remains a read-only, tool-free inference over the saved revision with freshly fetched backend instructions.

- Admission is synchronous with the shutdown, configuration-uncertainty, update apply/recovery, confirmed maintenance-quiesce and transition checks. At most one preview runs; a duplicate gets `OPERATION_IN_PROGRESS`. A preview requested while another operation holds the gate is refused with a retry hint, without side effects.
- A settings/restore/rollback/skill save cancels a running preview (its late output is discarded as `CANCELLED`) instead of being refused; manual upgrade and confirmed maintenance quiesce defer as before. Run, Stop and native Operator admission stay available and neither cancel the preview nor are undone by it.
- The endpoint, model, credentials and redaction set are captured together at admission. Output is discarded (`CANCELLED`) after Cancel, disconnect, the 60-second deadline, shutdown, an update lock, configuration uncertainty or a changed saved revision/credential; known secrets are rejected. Cancel, disconnect, the deadline and shutdown release the single preview slot within about a second even if a provider ignores abort, and shutdown awaits that release. Studio re-enables Preview only after its own Cancel request settles, so a delayed Cancel cannot abort or refuse the retry.

## Results and recovery

`GET /api/status` includes `transition`, `nativeActive`, and the latest nonsecret `lifecycle` (`id`, operation, phase, prior running intent, `applied`, `resumed`, actual `running` state at completion, fixed error/hint). The mutation response is the operation at acknowledgement (`applied`, local warnings, `phase` still in progress); stop/restart results and their warnings arrive in later status reads. Studio shows **Saved** first and then refreshes the canonical view; a failed refresh is reported as saved with a refresh warning, never as a failed save. Successful application with failed startup is **Applied, but Coach is not running**, not a failed save. **Retry Coach restart** calls only Run against the saved revision; it creates no revision and cannot replay a previous action.

Validation/write failures preserve the editor draft. The previous running configuration resumes only after its durable configuration and active credential binding are read back successfully. Ambiguous storage publication fails closed (`CONFIGURATION_STATE_UNCONFIRMED`) and fences subsequent admission; repair protected storage and verify canonical data before service restart. Authentication, input validation, true storage failure and concurrent-operation serialization (`OPERATION_IN_PROGRESS`) remain failures.

### Unresolved earlier work never blocks a valid save

A valid settings save, persona restore, skill save/restore or rollback is applied even when earlier work is unresolved or a cleanup/safety check fails. The save performs no reconciliation RPC and never waits for an exact proof. The outcome is `lifecycle.warnings` (`{code, hint}`), retained in `GET /api/status`; Studio renders every warning in the operation status on each status refresh; warnings known at acknowledgement (journal and delivery state) also appear in the save notice:

| Code                           | Meaning (what stays protected)                                                                                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTONOMY_WRITE_UNRESOLVED`    | A background Coach write's outcome is unknown. Its journal entry keeps its original identity, origin and account; it is never replayed and new background actions stay paused until exact proof.                     |
| `AUTONOMY_WRITE_REBOUND`       | As above, and the save changed the origin or Kata.fit token (`lifecycle.rebinding`, computed from the saved state, so a blank retained token is not a rebinding). Only the original connection/account can prove it. |
| `AUTONOMY_JOURNAL_UNCONFIRMED` | The autonomy write journal or owned-container cleanup is unreadable/pending. Nothing is deleted; background claims stay paused.                                                                                      |
| `ACTION_DELIVERY_UNRESOLVED`   | A member message or action delivery is unconfirmed. It stays bound to its account and is never re-sent.                                                                                                              |
| `NATIVE_CLEANUP_UNCONFIRMED`   | Native teardown failed. Ownership is retained; new native sessions stay refused until Stop native session confirms cleanup.                                                                                          |
| `WORKER_STOP_UNCONFIRMED`      | The stopped Worker's backend stop or a reply publication is unconfirmed. That instance is retained and never replaced by the save.                                                                                   |

When Coach was running and its stop, publication safety or native cleanup is unconfirmed, the saved revision is not started: `lifecycle.restartPending` is true, `resumed` false, and Studio shows **Saved. Coach restart pending; Coach is not running.** with **Retry Coach restart**. If the previous Worker never stopped (`running` true), Studio instead says the previous Coach may still be running and the saved revision was not started, without Retry (Run cannot replace a running Worker; Stop first). Retry (`POST /api/run`) first makes one bounded presence recovery or receipt-only publication read with the stopped instance's own credentials, then starts only the saved revision; while evidence is still missing it returns `WORKER_STOP_UNCONFIRMED`.

A Retry can recover an initial presence-registration reply loss without resaving settings: after local Stop settles, one bounded recovery obtains a validated generation for the same instance ID and confirms its Stop before replacement. This path is single-flight under the lifecycle gate; Stop and shutdown join it, and shutdown prevents restart. Denied, stale, malformed or unavailable evidence still blocks replacement. It does not claim work, run inference, replay a task or bypass unresolved publication fences.

Settings/restore/rollback support a UUID `operationId` with `expectedRevision`. The server retains a bounded private in-memory replay cache (32 responses, no request bodies); identical accepted retries return the original outcome, while reused identities with different payloads and stale revisions fail closed. Revision comparison continues to prevent a repeated committed save even after cache eviction or process replacement. These are local request-loss protections, not a durable general transaction queue. The UI does not automatically resend a mutation: after a lost reply it retains the draft, reads back the saved revision and says whether the save is visible there; a failed read leaves no lock or uncertainty flag (only a dispatched POST is ever uncertain). A server restart that loses the in-memory operation receipt requires checking persisted configuration before retry; never infer failure from transport loss. There is no promise to resume an interrupted settings operation after host death.

The browser fences late results by authenticated session and status-request generation. Lock/authorization expiry drops secret drafts and prevents old responses from mutating a newly unlocked session; already accepted server transitions still settle. Server shutdown waits for an accepted local write and its continuation, and suppresses restart after shutdown begins.

## Process-replacing manual updates

See [source updates](source-updates.md). The stable owner, not the browser, owns update recovery. Before update acceptance it durably fsyncs a bounded private `update-resume.json` record `{sha, pending:true}` when prior running intent requires resume. The normal source-operation journal remains separate. The owner retains the intent through preparation failure, candidate rollback, lost local HTTP responses and process restart, clears it only after authenticated running-state readback, and uses a bounded local-only recovery timer with no source check. Recovery starts the saved configuration only; it does not reinstall the SHA.

`manualRestartSupported` is explicit. Old stable owners cannot acquire the capability through an application-only source update: a running manual upgrade fails before stop/apply with actionable launcher-replacement guidance. `recovering` gates application mutations/native admission while the owner restores running intent. If recovery cannot be confirmed, the source result and restart result remain separate; Retry is startup-only. A legacy rollback child without the dedicated recovery endpoint uses its existing authenticated Run endpoint.
