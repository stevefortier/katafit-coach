# Confirmed Coach stop / apply / restart

Settings Save, persona-history Restore, legacy `POST /api/rollback`, and saved-revision Preview share one server-owned transition. The browser never races separate Stop, Save and Run calls.

- Running Coach or active native Pi requires explicit acceptance (`confirmRestart: true`). Missing/false consent returns `RESTART_CONFIRMATION_REQUIRED` without stopping or writing. Native browser confirmations are keyboard/screen-reader accessible; Cancel retains drafts. Restore also discloses which persona drafts are replaced and which connection drafts remain unsaved.
- Capture running intent at server admission, not from a stale browser status. An intentionally stopped Coach stays stopped. Stop aborts polling and awaits active work plus presence-generation acknowledgement. Native terminal teardown is awaited before configuration publication. A new Worker captures the resulting endpoint, model, vision flag and credential together.
- The server gate excludes concurrent Run, Stop, settings/restore/rollback, preview, manual upgrade, automatic quiesce and native-ticket/WebSocket admission until recovery completes. Read-only status remains available. Preview Cancel aborts inference and then resumes prior running intent; no user chat, action, or terminal input is replayed.
- Persona restore copies only persona fields into a new revision. Legacy rollback retains Store's configuration/credential binding rules; it is an API compatibility path, not an extra Studio editor.

## Results and recovery

`GET /api/status` includes `transition`, `nativeActive`, and the latest nonsecret `lifecycle` (`id`, operation, phase, prior running intent, `applied`, `resumed`, actual `running` state at completion, fixed error/hint). If native teardown fails before the worker stops, the outcome explicitly reports that the previous configuration is still running; lack of a restart is not proof of a stopped worker. The mutation response carries the same outcome after restart settles. Successful application with failed startup is **Applied, but Coach is not running**, not a failed save. **Retry Coach restart** calls only Run against the saved revision; it creates no revision and cannot replay a previous action.

Validation/write failures preserve the editor draft. The previous running configuration resumes only after its durable configuration and active credential binding are read back successfully. Ambiguous storage publication fails closed (`CONFIGURATION_STATE_UNCONFIRMED`) and fences subsequent admission; repair protected storage and verify canonical data before service restart. Stop acknowledgement failure and unresolved publication identities are also real blockers (`WORKER_STOP_UNCONFIRMED`), not errors to hide by bypassing the worker guard. Check backend connectivity and canonical receipts. Native cleanup failure retains its existing admission barrier.

Settings/restore/rollback support a UUID `operationId` with `expectedRevision`. The server retains a bounded private in-memory replay cache (32 responses, no request bodies); identical accepted retries return the original outcome, while reused identities with different payloads and stale revisions fail closed. Revision comparison continues to prevent a repeated committed save even after cache eviction or process replacement. These are local request-loss protections, not a durable general transaction queue. The UI does not automatically resend a mutation: after a lost reply it retains the draft, locks mutation controls and checks the matching lifecycle status. A server restart that loses the in-memory operation receipt requires checking persisted configuration before retry; never infer failure from transport loss. There is no promise to resume an interrupted settings operation after host death.

The browser fences late results by authenticated session and status-request generation. Lock/authorization expiry drops secret drafts and prevents old responses from mutating a newly unlocked session; already accepted server transitions still settle. Server shutdown waits for an accepted transition and suppresses restart after shutdown begins.

## Process-replacing manual updates

See [source updates](source-updates.md). The stable owner, not the browser, owns update recovery. Before update acceptance it durably fsyncs a bounded private `update-resume.json` record `{sha, pending:true}` when prior running intent requires resume. The normal source-operation journal remains separate. The owner retains the intent through preparation failure, candidate rollback, lost local HTTP responses and process restart, clears it only after authenticated running-state readback, and uses the existing bounded recovery cadence before any further automatic update check. Recovery starts the saved configuration only; it does not reinstall the SHA.

`manualRestartSupported` is explicit. Old stable owners cannot acquire the capability through an application-only source update: a running manual upgrade fails before stop/apply with actionable launcher-replacement guidance. `recovering` gates application mutations/native admission while the owner restores running intent. If recovery cannot be confirmed, the source result and restart result remain separate; Retry is startup-only. A legacy rollback child without the dedicated recovery endpoint uses its existing authenticated Run endpoint.
