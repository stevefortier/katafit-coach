# Installation-local Dojo MCP (registration-only, runtime disabled)

Studio's authenticated installation administrator can save/remove up to eight local endpoint registrations. URLs must be canonical `http://127.0.0.1:<nonprivileged-port>/<path>`; credentials are stored privately in the installation home and never returned by the admin API. **Neither the Studio admin key nor a Dojo-scoped Coach connection credential proves the current Kata.fit chief or binds a registration to a Dojo.** Registered endpoints are inert: the worker does not contact them, list tools, or offer local MCP tools to Pi in any scope. There is no feature flag or credential-only bypass. Personal requests, previews, operator chat and typed tasks remain excluded. This is not an app-managed MCP registration feature.

## Required backend contract before runtime can be implemented

The app/backend owner must agree on and implement an authenticated, versioned contract rather than the standalone worker inventing authority. At minimum:

1. **Registration authorization:** server-verified current chief identity and explicit Dojo ID bound to each registration, with the permitted endpoint/catalog identity and revocation generation. Installation admin authentication alone cannot authorize any member-affecting tool. Define chief transfer, removal, registration rotation and migration of already-saved unbound records; old records must remain inert absent fresh authoritative binding.
2. **Request-bound discovery:** given an authenticated worker credential, exact `{request_id, lease_generation}` and registration ID, the backend checks current Dojo, chief, credential, requester/scope, Clear and lease/deadline state and returns only an authorized finite catalog/authorization version. Do not infer authority from a previously read context, scope string or annotations.
3. **Per-call dispatch:** immediately before **each** external call, a backend-authoritative check/capability must bind request ID, lease generation, registration/catalog version, tool name, current chief/Dojo and scope/revocation, with a bounded expiry and definitive denial. The backend and worker must define the race between validation and side effect: either dispatch is mediated by the authoritative backend with an atomic fence, or a one-use capability is verified by the external service at commit. A worker-side read followed by an unfenced HTTP call is not sufficient if authority can change between them. Cancellation and local timeout alone do not prove revocation. Recheck final result/publication independently.
4. **Ambiguous outcome:** persist a stable per-action idempotency key before dispatch; the receiver must deduplicate and expose an independently readable canonical receipt (`committed`, `definitively_not_sent`, or `unknown`) tied to the same key and request authority. Timeout, cancellation, malformed/oversized result or lost acknowledgement **cannot** imply unsent. Reconciliation must never resend the action. The worker must not automatically retry an unknown mutation and must surface a content-free receipt/status to the member/operator when appropriate.
5. **Local transport:** retain loopback-only URL validation and redirect rejection. Specify local server identity/authentication and port-replacement threat model; a reusable bearer alone can be captured by another same-host process taking over the port. Bound transport bytes, schema and results and reject non-text results until explicitly supported.

These are **protocol dependencies, not existing endpoints**. The current Studio row says "Unbound · inactive" and the save confirmation does not imply discovery or Dojo ownership; even previously saved entries remain inert. App PR #792 and its stacked worker API must be reviewed for exact shapes, transactional fences, negative/expiry semantics and receipt lifecycle before enabling runtime. Automatic model tool selection (without per-call human approval) is the selected UX *only after* the authoritative contract is delivered and independently tested. A future failure should be presented as **outcome unknown; never retry automatically; inspect/reconcile the external system**. The Pi sanitizer already uses this wording for any local-MCP-namespaced tool error and blocks subsequent local MCP tool calls in that inference turn, including a model-selected retry after a possibly committed action. This is defensive behavior while registration runtime is disabled, not a substitute for a durable receipt or proof of safe durable mutation delivery across cancellation, restart or revocation.
