# Installation-local Dojo MCP tools (pilot)

The authenticated, loopback-only Studio lets the **installation administrator** register an already-running local MCP Streamable HTTP server in Settings → Local MCP. Use a chief-controlled installation and a Dojo-scoped Kata.fit credential. This UI does **not** verify a Kata.fit chief identity separately from the installation admin key, and it never launches a command. Registration permits only canonical `http://127.0.0.1:<nonprivileged-port>/<path>` URLs: no DNS hostnames, remote URLs, query/userinfo/fragments, redirects, or browser-provided shell commands. Choose the local server and its capabilities carefully: the model selects tools automatically, including possible mutations, without per-call approval. Studio discloses this and the worker instructs the model to disclose its intended action; instructions are not an enforcement boundary.

An optional bearer credential lives only in the installation's private `local-mcp.json` (0600 under the protected home), never in registration responses, tool schemas or provider requests. This is private storage, not encryption against another process running as the same OS user. The local MCP server itself authenticates its callers and enforces its own action permissions. A server without a bearer credential relies on the local-host trust boundary. Avoid sharing the Studio host with untrusted local processes.

On each **claimed Dojo main-chat request**, the worker initializes each registered endpoint, sends `notifications/initialized`, lists its tools and offers validated, namespaced `local_mcp__<registration-id>__<tool-name>` definitions to Pi. Personal requests, task generation, Studio preview and Operator chat receive none. Backend-authorized read tools remain separate. Eight registrations and sixteen tools per server are permitted. Schemas, argument bytes, response bytes, time (five seconds per RPC), model envelope, and total model tool turns are bounded. Only text MCP results are supported; SSE responses and non-text results fail closed. Removing a registration aborts its current request-local session and blocks later dispatch; an already-delivered side effect cannot be recalled. Stopping or timing out the worker also aborts sessions. A failed/ambiguous call is not evidence that the external mutation was not committed—inspect the external system before retrying.

**Separate backend contract:** Kata.fit app-owned personal/Dojo MCP registrations are not loaded, mirrored, or invoked here. A later backend PR must define owner-scoped catalog discovery and call authority, request/lease binding, per-call reauthorization, cancellation/revocation and bounded results. Combine those authorized tools at the worker request-local catalog boundary, never by copying app credentials into this installation or inventing an endpoint. This slice proves only installation-local Dojo MCP tools with a synthetic provider, not live Kata.fit app-managed integrations or live model behavior.
