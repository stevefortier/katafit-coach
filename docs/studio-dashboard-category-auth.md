# Dashboard category authorization (human Studio)

The human-only `studio_dashboard_overview` v1 response is paged and chief-authorized. Each member carries `category_access: { training, nutrition, body }`, each value `shared` or `not_shared`, plus `charts: { training, nutrition, body, limitations }`. An authorized category has an array (possibly empty); an unauthorized category has `null`. `limitations` may be `null` when every category is unshared; otherwise it is a bounded nonempty string. Unknown fields, missing access states, and contradictory access/series shapes fail closed. `photo_access` and `photos` are independent of all chart categories. The overview preserves the backend's current media-read credential prerequisite; this consumer change does not make chart requests independently callable without Media scope.

Training points derive only from authorized workout activity, nutrition from meal activity, and body from metric/measurement activity. Dashboard coverage counts each category separately among the shown roster. A zero-share category says no shown members share it; a shared category with no points says no shared data in the period. Neither represents missing days as zero. Photo bytes remain fetched through the separately reauthorized `studio_dashboard_read_photo` endpoint and never through the chart snapshot.

## Rollout

Deploy the backend and Coach together where possible. A new Coach rejects the older `stats_access` overview rather than interpreting Stats as activity authorization. An older Coach rejects the new category-shaped overview rather than rendering graphs from a stale Stats gate. During a rolling mismatch, Dashboard may show its unavailable/Refresh state and no graphs; media thumbnail reads remain independently authorized, but the old/new overview mismatch prevents populating the gallery in that client. This is preferable to leaking an unauthorized series. The category-specific backend must be verified before treating the new UI as usable. Do not reintroduce a Stats fallback.
